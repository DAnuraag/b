> [!WARNING]
> **Measurement scope.** The system measures **water-quality parameters**: pH, turbidity, TDS, EC and temperature. It does **not** chemically identify contaminants. pH, TDS, EC and turbidity **cannot** detect arsenic, lead, mercury, fluoride, nitrate, pesticides or pathogens. Screening for a specific contaminant needs a **dedicated detection or screening subsystem** (for example a field test kit, a colorimetric or electrochemical analyser, or laboratory analysis). The architecture has a place for one (see [§ 9.6](#96-dedicated-contaminant-screening-subsystem-optional-separate)), but the prototype does not include one.

# PART A: UNDERSTANDING THE SYSTEM

## 1. Problem Statement

### 1.1 Context

Communities in remote, rural and mining-affected regions often rely on groundwater, open wells, hand pumps, storage tanks or surface streams. In these places:

- **Water-quality changes can go unnoticed** for days or weeks. Sampling is manual, infrequent and depends on someone travelling to site.
- **Grid power is unreliable or missing.** Monitoring equipment that needs mains power is impractical.
- **Connectivity is intermittent.** Cellular coverage may be weak, congested or absent for hours.
- **Maintenance visits are rare.** Equipment must keep running, and report its own health, between visits.
- **Data is hard to trust.** Paper logs and single "SAFE / UNSAFE" indicators can't be audited, can't show *why* a decision was made, and can be edited after the fact.
- **Mining activity** can change water chemistry, for example through acid mine drainage that affects pH and dissolved solids, and through suspended sediment that affects turbidity. Changes in these general parameters can be an *early indication* that a more specific investigation is needed.

### 1.2 What goes wrong with typical student IoT prototypes

| Typical prototype behaviour | Field consequence |
|---|---|
| Sends data straight to the cloud and stores nothing locally | Every connectivity outage loses data permanently |
| Stores only "SAFE / UNSAFE" | No traceability; the decision can't be re-evaluated when thresholds change |
| Uses hard-coded thresholds of unknown origin | Wrong decisions presented with false confidence |
| Claims that TDS/pH "detects arsenic" | Scientifically false and potentially dangerous |
| Lets anyone edit the database | Records can be falsified with no trace |
| Assumes a USB power bank or mains supply | Stops working after hours or days in the field |
| No self-diagnostics | A disconnected sensor reports a plausible-looking constant value for weeks |
| Breadboard in a plastic lunch box | Corrosion, condensation and loose wires within weeks outdoors |

### 1.3 Problem definition

> **Design a monitoring platform that continuously collects water-quality parameter data from verified sensors, keeps every raw reading traceably, checks every reading against documented rules, keeps working without the internet or the grid, reports its own health, and gives an on-site engineer a simple, trustworthy view, without making claims the hardware can't support.**

### 1.4 Stakeholders

| Stakeholder | Needs | How the system serves them |
|---|---|---|
| On-site engineer / technician | Clear current state; what to do next; alerts that can be trusted | Simple dashboard, local buzzer/LED alerts, guided maintenance actions |
| Service engineer | Deep diagnostics without guesswork | Separate industrial debugger |
| Supervisor / programme manager | Historical, auditable records across sites | Firebase history, audit log, exports |
| Community / water users | Early warning that the water needs further investigation | Local alert; escalation path to authorities (process, not automated diagnosis) |
| Administrator | Control over configuration and access | Role-based access, audited configuration changes |
| Researchers / auditors | Trustworthy raw data | Raw values preserved, hash-chained, verification reasons stored |

### 1.5 Scope

| In scope (prototype) | Out of scope (prototype) |
|---|---|
| pH, turbidity, TDS, EC, temperature monitoring | Chemical identification of specific contaminants |
| Rule-based verification of data quality | Declaring water "potable" or "certified safe" |
| Offline storage and later synchronisation | Real-time guaranteed delivery over cellular |
| Solar + wind hybrid charging into one battery | Guaranteed operation in every weather condition |
| Engineer dashboard and service debugger | Consumer mobile app |
| Local audible/visual alerts | Automatic shut-off of community water supply (future, needs a safety review) |
| Purification-stage *monitoring hooks* (e.g. pre/post filter readings) | Design of a certified purification plant |

> **About "Purification" in the project name.** The platform monitors water around a purification stage, for example with sensor sets before and after a filter, and exposes a low-priority load channel (P4) for purification auxiliaries such as a small pump or UV-lamp controller. It does **not** claim to make water potable. Any purification hardware must be specified, validated and approved separately.

### 2.4 What makes this "field-grade" rather than "demo-grade"

| Concern | Demo-grade approach | This project's approach |
|---|---|---|
| Data loss on outage | Accepted | Designed out: local append-only store plus outbox |
| Trust in data | Implicit | Explicit: every record carries a verification result and a reason |
| Editing history | Possible | Blocked by Security Rules and DB triggers; corrections are audit events |
| Sensor failure | Silent | Detected: missing, out-of-range, stuck and inconsistent rules |
| Power | Assumed | Measured, budgeted, prioritised, mode-switched |
| Clock | Assumed correct | Validated: skew, monotonicity, RTC/NTP/GSM time sources |
| Configuration | Hard-coded | Versioned config files; thresholds `TBD / CONFIGURABLE` |
| Claims | Aspirational | Bounded: explicit limitations section and SIMULATED labels |

## 3. Engineering Principles & Honest Claims Policy

### 3.1 Ten engineering principles

1. **Raw data is sacred.** Never overwrite, never delete, never "clean" a raw reading in place.
2. **Verification is classification, not truth.** The engine classifies readings against documented rules. It does not decide whether a chemical measurement is scientifically "true".
3. **Every rule is documented.** A rule that isn't in the [Rule Catalogue](#124-verification-rule-catalogue) doesn't exist in code.
4. **No invented thresholds.** Water-quality attention bands are disabled by default and must come from a verified source or an explicit project decision, recorded in configuration with its source.
5. **Offline is the normal case.** Cloud connectivity is a bonus, not a dependency.
6. **Local safety first.** Emergency alerts must work with no internet.
7. **Measure, don't assume.** Power generation comes from voltage and current sensors, never inferred from the weather.
8. **Least privilege.** Engineers can view and acknowledge. They can't rewrite history.
9. **Configurable, not hard-coded.** Every electrical rating, interval and threshold lives in configuration.
10. **Test before you claim.** A capability is "supported" only when a documented test passes.

### 3.2 Claims policy

| ❌ Never write | ✅ Write instead |
|---|---|
| "Detects arsenic / heavy metals" | "Monitors water-quality parameters; contaminant screening requires a dedicated detection method" |
| "Water is SAFE" | "All configured parameters within configured bands; verification PASSED" |
| "IP67 waterproof" | "Designed for outdoor use with gasketed enclosure; ingress rating **not tested**" |
| "Military-grade security" | "Reasonable security practices: authentication, RBAC, TLS where supported, audit logging" |
| "Works in all weather" | "Designed to improve energy availability under variable weather; operation depends on measured generation and battery reserve" |
| "Industrial certified" | "Prototype; certification path described in §47" |
| "Battery lasts 30 days" | "Autonomy = usable capacity ÷ average load; both `TBD / CONFIGURABLE`, measured during Phase 13" |
| "Toxic level: TDS > X" | "ABN-001 attention band for TDS: `TBD / CONFIGURABLE`, source: ________" |

### 3.3 Terminology used in this document

| Term | Meaning in this project |
|---|---|
| **Water-quality parameter monitoring** | Continuous measurement of pH, turbidity, TDS, EC and temperature |
| **Verification** | Applying documented data-quality rules to a raw reading and recording the outcome |
| **Screening** | A dedicated, separate method aimed at a specific contaminant (not part of the core sensor set) |
| **Attention band** | Project-configured range outside which a reading is flagged `ABNORMAL` for human follow-up. It is not a safety verdict |
| **Sensor operating range** | The range the sensor hardware can physically report (from its datasheet). Values outside it suggest a sensor fault |
| **Prototype** | Built and tested at bench or pilot scale; not certified |
| **Industrial deployment capability** | A future target that needs further engineering, testing and certification |
| **`TBD / CONFIGURABLE`** | A value not decided yet; must be set in configuration before deployment |
