### 4.4 Why both an ESP32 and a Raspberry Pi?

| Aspect | ESP32 | Raspberry Pi |
|---|---|---|
| Role | Real-time field I/O, deep sleep, deterministic sampling | Trusted processing, storage, sync, diagnostics |
| Power profile | Very low in deep sleep (measure on your board) | Much higher; can't practically deep-sleep like an MCU |
| Storage | Small flash; ring buffer only | SD/SSD; database-scale storage |
| OS | Bare-metal / FreeRTOS | Linux (systemd services) |
| Failure isolation | Keeps sensing and local alerting if the Pi is down | Keeps storing and verifying if the cloud is down |
| Update frequency | Rare (OTA with care) | More frequent (packages, services) |

The split means that a failure at any single layer doesn't stop sensing:

```text
Cloud down   → Pi stores + queues          → no data loss
Pi down      → ESP32 ring-buffers + alerts → bounded data loss protection
Modem down   → Pi stores + queues          → no data loss
Grid absent  → hybrid renewables + battery → designed-for condition
Battery low  → LOW-POWER mode, load shedding (P3/P4 first)
```

### 4.5 Deployment topologies

| Topology | Description | When to use |
|---|---|---|
| **T1: Co-located** | ESP32 and Pi in the same enclosure, UART link | Single-site pilot (default prototype) |
| **T2: Star** | Several ESP32 nodes → one Pi gateway over RS-485 or Wi-Fi | Several sampling points within tens to hundreds of metres |
| **T3: Node-direct** | ESP32 + cellular modem → Firebase; no Pi | Very low-power sites; loses edge verification (the cloud function runs the same engine) |
| **T4: Hybrid** | T1/T2 with cellular fallback directly from the ESP32 | High-value sites where the Pi is a single point of failure |

> **Default for this project: T1, with T4's fallback path optional.**

## 5. Data Flow

### 5.1 End-to-end pipeline

<p align="center"><img src="diagrams/03_data_pipeline.png" alt="Data pipeline" width="100%"/></p>

<sub>Figure 5.1: Raw data pipeline. The raw row is committed before verification runs.</sub>

### 5.2 Step-by-step

| Step | Where | Action | Output | Failure handling |
|:-:|---|---|---|---|
| 1 | ESP32 | Read each sensor N times, median filter (N configurable) | Raw electrical/converted values | Missing sensor → field set to `null`, never a fake value |
| 2 | ESP32 | Apply stored calibration coefficients (version-tagged) | Engineering-unit values + `cal_version` | Missing calibration → `cal_state: "UNCALIBRATED"` flag |
| 3 | ESP32 | Build frame: IDs, device timestamp, `boot_id`, `seq`, mode, power, comms | Raw JSON | Buffered in RTC/flash ring buffer |
| 4 | ESP32 → Pi | Send framed JSON with CRC-16 | Bytes on the wire | No ACK → retry, then keep in ring buffer |
| 5 | Pi | Check CRC, parse JSON, stamp `received_ts` | Parsed message | Bad CRC → `frame_error` event, NACK |
| 6 | Pi | **INSERT raw row** (append-only) + `raw_sha256` + chain hash | `raw_readings` row | DB error → local file spool (last resort) |
| 7 | Pi | Run verification engine | `verification_results` row | Engine exception → `ENGINE_ERROR` event; raw is already safe |
| 8 | Pi | Raise events/alerts from results | `events` rows, buzzer command | Local alert works offline |
| 9 | Pi | Enqueue raw + result + events into `sync_outbox` | `PENDING` rows | — |
| 10 | Pi → Cloud | Sync engine batches, upserts by deterministic ID | Firestore docs | Backoff; stays `PENDING` |
| 11 | Cloud | Security Rules reject updates/deletes on raw and audit | Immutable replica | Rule violation → denied + logged |
| 12 | UI | Dashboard subscribes; debugger queries edge API | Views | Stale-data banner if last sync is too old |

    "turbidity_ntu": 4.81,
    "tds_ppm": 212.4,
    "ec_us_cm": 426.1,
    "temperature_c": 26.42
  },
  "raw_electrical": {
    "ph_mv": 1412.0, "turbidity_mv": 3021.0, "tds_mv": 611.0, "ec_mv": 702.0

> **Why `raw_electrical`?** Keeping the pre-calibration electrical value (millivolts) alongside the engineering value means a later calibration correction can be *re-computed* from the original signal, and filed as an audit event, without touching the raw record.

### 5.4 Identifier strategy

| Identifier | Format | Generated by | Uniqueness guarantee |
|---|---|---|---|
| `node_id` | `SWN-NNNN` | Provisioning (admin) | Registry in Firebase `nodes/` |
| `sensor_id` | `<TYPE>-<NN>` + serial in registry | Provisioning | Registry per node |
| `boot_id` | uint, incremented and persisted in NVS on every boot | ESP32 | Monotonic per node |
| `seq` | uint32, reset on boot | ESP32 | Monotonic within a boot |
| `record_id` | `<node_id>-<boot_id:05d>-<seq:08d>` | ESP32 | Globally unique (node × boot × seq) |
| `result_id` | `<record_id>#v<engine_version>` | Pi | One result per record per engine version |
| `event_id` | UUIDv7 (time-ordered) | Pi | Random + time |
| `audit_id` | UUIDv7 | Pi / Cloud Function | Random + time |

Because the `record_id` is deterministic, **the same reading always maps to the same Firestore document**. A re-sent frame after a lost ACK, or a re-synced batch after a timeout, overwrites nothing and creates no duplicate. See [§15](#15-offline-first-operation).

### 5.5 Data retention (defaults, configurable)

| Store | Retention | Rationale |
|---|---|---|
| ESP32 ring buffer | Last N frames (N = `TBD / CONFIGURABLE`, flash-limited) | Survive a Pi outage |
| Pi `raw_readings` | Indefinite (rotate to archive files when storage > threshold) | Authoritative local record |
| Pi `sync_outbox` | Until ACKED + 7 days | Debugging sync issues |
| Pi log files | 30 days, rotated | Troubleshooting |
| Firestore `readings` | Indefinite (or export to cold storage) | Cloud history |
| Firestore `audit` | Indefinite | Traceability |

## 6. Power Flow & Hybrid Renewable Architecture

### 6.1 Architecture

<p align="center"><img src="diagrams/02_power_architecture.png" alt="Hybrid power architecture" width="100%"/></p>

<sub>Figure 6.1: Hybrid renewable power architecture. All ratings are <code>TBD / CONFIGURABLE</code>.</sub>

```text
SOLAR PANEL  ──►  SOLAR CHARGE CONTROLLER (PWM/MPPT)       ──┐
                                                             ├──►  BATTERY  ──►  PROTECTION  ──►  LOAD-PRIORITY BUS
WIND TURBINE ──►  RECTIFIER + WIND CHARGE CONTROLLER       ──┘                   (fuse, TVS,      P1 ESP32 + sensors
                  (+ dump load / brake for over-speed)                          reverse-pol.,     P1 Local alert
                                                                                 LVD)              P2 Raspberry Pi
                          POWER MONITOR (V/I per source, battery, load)                            P3 Cellular modem
                                                                                                   P4 Purification aux.
```

### 6.2 Design rules

1. **One controller per source.** Solar and wind have very different electrical behaviour. PV is a current-limited DC source; a small turbine gives variable-frequency AC (or wild DC) and must never be left open-circuit at high wind speed. Never connect a turbine to a solar-only controller.
2. **Common battery.** Both controllers charge the same battery. The controllers, battery chemistry and charge profiles must be compatible (for example the same absorption/float set-points). `TBD / CONFIGURABLE`.
3. **Wind over-speed protection.** The wind controller must provide a dump (diversion) load and/or electrical braking, and the turbine should support mechanical furling where available.
4. **Measured, not assumed.** Each source has its own voltage/current measurement. The system never *infers* generation from the weather.
5. **Low-voltage disconnect (LVD).** A hardware LVD protects the battery from deep discharge, independently of the firmware.
6. **Protection on every branch.** Fuses sized for the conductor, TVS diodes on long cable runs, reverse-polarity protection, and a common earth/bonding point.

### 6.3 Source availability scenarios

| # | Solar | Wind | Battery role | System behaviour |
|:-:|:-:|:-:|---|---|
| 1 | ✅ available | ❌ unavailable | Charges from solar surplus; supplies at night | NORMAL if SoC is healthy |
| 2 | ❌ unavailable | ✅ available | Charges from wind surplus | NORMAL if wind covers the load |
| 3 | ✅ available | ✅ available | Charges fastest | NORMAL; purification aux (P4) may be enabled |
| 4 | ❌ unavailable | ❌ unavailable | **Sole supply**: BATTERY → LOAD | NORMAL until `LOW_ENTER`, then LOW-POWER; CRITICAL sheds P2–P4 |

> **No source is assumed to always be available.** The four scenarios are tested explicitly (see [Power tests PW-01…PW-09](#466-power-tests)).

**Reading these figures:**

- Day 1 (sunny, low wind): solar charges the battery during daylight; the battery carries the night.
- Day 2 (cloudy, windy): wind makes up for reduced solar and the battery stays healthy.
- Day 3 (rain, intermittent wind): generation often falls below load, so the battery discharges. If SoC falls below `LOW_ENTER`, LOW-POWER mode reduces load.
- Day 4 (storm): gusty wind contributes, but over-speed protection can brake the turbine, so wind generation drops to zero during the strongest gusts. This is why weather alone can't predict generation.

## 7. Communication Architecture

### 7.1 Paths

```text
PRIMARY (local, always)           CLOUD (when available)              FALLBACK (optional, T4)
ESP32                              Raspberry Pi                         ESP32
  │ UART / RS-485                    │ HTTPS/TLS                           │ UART (AT)
  ▼                                  ▼                                     ▼
Raspberry Pi                       Router / USB modem                   Cellular module (e.g. SIM800L)
  │                                  │                                     │ GPRS/2G (region-dependent)
  ▼                                  ▼                                     ▼
Local storage (SQLite)             Firebase                             Relay endpoint / Firebase
```

> **Cellular note.** SIM800L-class modules are 2G/GPRS devices. **2G networks are being shut down in several countries and regions**, so check local operator support before choosing a module. A 4G LTE Cat-M1/NB-IoT/Cat-1 module is the likely upgrade path and is kept behind the same `CommLink` interface. SIM800L-class modules also draw **high peak current during transmit bursts** and need a supply that can deliver it, with bulk capacitance close to the module (value `TBD / CONFIGURABLE` from the module datasheet).

### 7.2 Local link framing (ESP32 → Pi)

```text
┌──────┬──────┬────────┬───────────────────────────┬────────┬──────┐
│ 0x02 │ VER  │ LEN(2) │ JSON payload (UTF-8)       │ CRC16  │ 0x03 │
│ STX  │ 0x01 │ BE u16 │ ≤ 1024 bytes (configurable)│ CCITT  │ ETX  │
└──────┴──────┴────────┴───────────────────────────┴────────┴──────┘
Pi replies:  ACK <record_id>\n   or   NACK <reason>\n
```

- CRC-16/CCITT-FALSE over `VER | LEN | payload`.
- The ESP32 retries up to `link.max_retries` times (default 3) with `link.retry_backoff_ms`.
- Frames that are never ACKed stay in the ESP32 ring buffer and are replayed, oldest first, after the link recovers.
- The Pi treats a replayed `record_id` that it already stored as **ACK without re-insert** (idempotent).

### 7.3 Cloud link

- Firebase Admin SDK (Python) on the Pi, authenticated with a **service account whose key file never enters Git** (loaded from the `GOOGLE_APPLICATION_CREDENTIALS` path or a secret store).
- Batched writes (≤ 500 operations per batch, per Firestore limits). Default batch size: 100.
- Document ID = `record_id`, which makes writes idempotent.
- Exponential backoff: `delay = min(max_delay, base × 2^attempt) + jitter`.

### 7.4 Communication status model

| State | Meaning | Detected by | Dashboard display |
|---|---|---|---|
| `LINK_OK` | ESP32 ↔ Pi frames ACKed | Pi receiver | Node ONLINE |
| `LINK_DEGRADED` | CRC errors or retries above threshold | Pi receiver counters | Node ONLINE (warning) |
| `LINK_DOWN` | No frame for > `heartbeat_timeout` | Pi watchdog | Node OFFLINE |
| `CLOUD_OK` | Last sync < `sync_stale_after` | Sync engine | Synced |
| `CLOUD_QUEUED` | Records pending, network down | Sync engine | "N records queued" |
| `CLOUD_AUTH_ERROR` | Credentials rejected | Sync engine | Debugger only + admin alert |
| `MODEM_NOT_REGISTERED` | AT+CREG not registered | ESP32 / Pi | Debugger: cellular panel |

### 8.4 Analog sensor interference

Several low-cost pH, EC and TDS modules share a common ground through the water. If they're powered at the same time from the same supply, the probes can interfere with each other and give wrong readings. Mitigations, in order of preference:

1. **Galvanic isolation** of each analog probe (isolated DC-DC plus isolated signal path).
2. **Time-multiplexed excitation**: power one conductivity-type probe at a time, and let it settle for `TBD / CONFIGURABLE` ms before reading.
3. **Physical separation** of the probes in the flow cell.

This is verified by test **SN-06** (cross-interference): each probe's reading must stay within tolerance when the other probes are switched on or off.

### 9.2 Environmental threat → design response

| Threat | Effect on system | Design response | Verification (planned) |
|---|---|---|---|
| **Dust** | Connector contamination, fan/vent clogging, optical sensor fouling | Sealed enclosure, gasketed lid, no fans (passive cooling), dust caps on unused connectors | Visual inspection after pilot period; dust exposure test (future) |
| **Rain** | Water ingress, short circuits, corrosion | Cable glands on the bottom face only, drip loops, sloped rain hood, sealed connectors | Hose/spray test (informal, not a rated test) |
| **Humidity / condensation** | Corrosion, leakage currents, ADC drift | Breather/pressure-equalisation vent, desiccant pack, conformal coating on PCBs (optional) | Humidity logging inside enclosure (internal RH sensor, optional) |
| **Temperature variation** | Component derating, battery performance change, sensor drift | Sun shield, light-coloured enclosure, battery in a separate compartment, temperature compensation for EC/TDS | Internal temperature logging |
| **Solar UV** | Plastic embrittlement, cable jacket degradation | UV-stable enclosure material, UV-rated cable, conduit | Periodic inspection |
| **Electrical noise** | ADC noise, false readings, resets | Shielded sensor cables, star grounding, ferrites, filtering, median sampling, isolated analog front-ends | Noise-floor measurement in SN tests |
| **Lightning / surge** | Component destruction | Surge arrestor on antenna, TVS on long lines, earthing rod and bonding | Design review (surge testing is future work) |
| **Long-duration operation** | SD-card wear, memory leaks, clock drift | SSD or high-endurance SD, WAL mode, watchdogs on ESP32 and Pi, RTC with NTP/GSM sync | 7-day and 30-day soak tests |
| **Remote location** | Slow maintenance response | Self-diagnostics, remote debugger, low-power fallback | Integration tests |
| **Limited maintenance** | Sensor fouling, drift | Guard pipe, anti-fouling approach (TBD), calibration reminders | Maintenance schedule (§44) |
| **Theft / vandalism** | Loss of equipment | Tamper-resistant fasteners, lockable enclosure, height mounting, optional door switch | Door-open event test |
| **Animals / insects** | Chewed cables, nests | Conduit, sealed glands, mesh on vents | Inspection |
| **Wind loading** | Mast/turbine damage | Guyed mast, turbine furling/brake | Structural review (future) |

### 9.3 Cable & connector practice

- Use **waterproof circular connectors** (where applicable) for sensors, so a probe can be swapped without opening the main enclosure.
- **Cable glands** sized to the cable outer diameter; unused glands blanked.
- **Drip loops** below every entry point.
- Sensor cables run in **flexible conduit** to the guard pipe.
- **Label** every cable at both ends with a sensor ID that matches the registry (`PH-01` and so on).
- Keep **power and analog signal cables separate**, and cross them at 90° where they must cross.

### 9.4 Sensor protection

| Measure | Purpose |

| Probe holders with depth stop | Repeatable positioning after maintenance |
| Wet storage caps for pH probe during transport | Glass electrodes must not dry out |
| Anti-fouling strategy (wiper, shade, or cleaning schedule) | Turbidity and EC surfaces foul over time: `TBD / CONFIGURABLE` |
| Quick-release mounts | Faster maintenance |

### 9.5 Serviceability

- All field-replaceable units (FRUs) are reachable without removing the enclosure from the pole.
- Each FRU has a **debugger procedure** (see [§19](#19-industrial-debugger)) to verify it after replacement.
- Maintenance actions are **logged as events** (who, when, what), and are never used to alter raw data.

| FRU | Replace without tools? | Post-replacement check |
|---|:-:|---|
| pH probe | ✅ (connector) | Calibration + DIAG-SN-PH |
| Turbidity / EC / TDS probe | ✅ (connector) | Calibration + DIAG-SN-xx |
| Temperature probe | ✅ | Comparison against reference thermometer |
| ESP32 board | ❌ (screwdriver) | Provision node ID, firmware check, full diagnostic |
| Raspberry Pi / SSD | ❌ | Restore config, DB integrity check, sync test |
| Modem / SIM | ❌ | Registration + signal check |
| Battery | ❌ | Voltage, polarity, charge test |

### 9.6 Dedicated contaminant screening subsystem (optional, separate)

The core sensors measure **general water-quality parameters**. If a project needs screening for a specific contaminant (for example arsenic in some groundwater regions, or heavy metals near mining sites), treat it as a **separate subsystem**:

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ DEDICATED SCREENING SUBSYSTEM (optional, NOT part of the prototype)          │
│                                                                              │
│  Method examples (to be selected with domain experts):                       │
│   • Field test kits (manual, result entered as a SCREENING event)            │
│   • Automated colorimetric / electrochemical analyser (vendor-specific)      │
│   • Scheduled sample collection → accredited laboratory analysis             │
│                                                                              │
│  Integration:                                                                │
│   • Results stored in a SEPARATE `screening_results` collection              │
│   • Each result records: method, analyte, value, unit, LOD, operator/device, │
│     sample ID, chain-of-custody reference                                    │
│   • Core verification engine NEVER infers analyte presence from pH/TDS/EC    │
└──────────────────────────────────────────────────────────────────────────────┘
```

Core-parameter changes, such as a sudden pH drop or a sharp EC rise, may **prompt** screening under a project procedure. They are never reported as detection of a contaminant.
